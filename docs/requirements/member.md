# 회원 가입

## 사용자 스토리

방문자로서, 쇼핑몰의 혜택을 받을 수 있도록 회원으로 가입하고 싶다.

## 비즈니스 규칙

- 방문자는 이름을 입력해 회원으로 가입할 수 있다.
- 가입한 회원은 식별자로 조회할 수 있고, 이름과 등급을 확인할 수 있다.
- 새로 가입한 회원의 등급은 일반이다.
- 회원 이름은 비어 있을 수 없다. 가입이 거절되면 거절 사유를 알려 준다.

## 전제

- 회원 엔티티(`Member`)와 회원 테이블은 이미 있다. 가입·조회 API는 없다.
- 회원 인증(로그인·비밀번호)은 범위 밖이다.
- 회원 정보 수정·탈퇴, 등급 변경은 범위 밖이다.

## API (참고용, 세부 형식은 자유)

| 기능 | 메서드 | 경로 |
| --- | --- | --- |
| 회원 가입 | POST | `/members` |
| 회원 조회 | GET | `/members/{memberId}` |

## 진행 방법

`CLAUDE.md`의 ATDD 워크플로우(체크포인트 1~8)를 따른다.

1. 위 규칙을 인수 조건으로 정리한다. 규칙에서 모호하거나 빠진 부분이 보이면 **가정하지 말고 PO에게 질문**하고, 답변을 `docs/decision-log.md`에 남긴다.
2. 확정한 인수 조건을 `src/acceptance/resources/features/member.feature`에 시나리오로 작성한다.
3. 시나리오 하나씩 Red → 설계 → 워킹 스켈레톤 → 도메인 TDD → Green 순서로 진행한다.

## 완료 기준

- [ ] 모든 인수 조건이 Cucumber 시나리오로 작성되어 있고, 구체적인 값과 도메인 언어로 쓰여 있다.
- [ ] 모든 시나리오가 API 경계(RestAssured)에서 검증하며 통과한다.
- [ ] 시나리오별로 Red 커밋(`test(acceptance):`)이 구현 커밋보다 앞서 있다.
- [ ] Red 커밋 이후 `.feature` 파일과 스텝 정의의 검증 로직이 변경되지 않았다.
- [ ] 이름 규칙과 처음 등급 규칙은 도메인 객체에 있고, 단위 테스트가 있다.
- [ ] PO 질문과 답변, 주요 설계 결정이 의사결정 로그에 남아 있다.
